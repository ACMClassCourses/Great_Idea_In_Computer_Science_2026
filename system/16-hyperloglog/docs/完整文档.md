# HyperLogLog 原理与项目说明

## 1. 我们要解决什么问题

一条数据流中可能有很多重复元素。

例如：

```text
alice
bob
alice
carol
bob
```

这里一共有 3 个不同元素。

这个数量叫做基数，英文是 cardinality。

最简单的做法是：

```cpp
std::set<std::string> seen;
```

每来一个元素，就放进 `set`。

最后使用：

```cpp
seen.size();
```

结果完全正确。

问题是，`set` 要保存所有不同元素。

如果有一亿个不同用户，就要保存一亿份数据。内存会不断增长。

HyperLogLog 选择另一条路：

- 不保存原始元素；
- 只保存少量统计信息；
- 允许一个小误差；
- 用固定大小的内存估计不同元素数量。

这就是本项目的核心问题。

## 2. HLL 的第一个直觉

先把一个元素做 64 位哈希。

一个好的哈希结果可以近似看成随机二进制串。

例如：

```text
001101...
```

从左往右找第一个 `1`。

如果第一个 `1` 在第 3 位，就记：

```text
rho = 3
```

随机二进制中：

- 第一位就是 `1`，概率约为 `1/2`；
- 前一位是 `0`，第二位才是 `1`，概率约为 `1/4`；
- 前 9 位都是 `0`，第 10 位才是 `1`，概率约为 `1/1024`。

所以，较大的 `rho` 很少见。

如果我们见到了很大的 `rho`，说明我们大概率已经看过很多不同元素。

这不是精确计数。

它只是一种概率上的判断。

## 3. 为什么不能只记一个最大值

假设只保存整个数据流中最大的 `rho`。

这样很容易被一次偶然情况影响。

例如，数据其实不多，但刚好出现了一个很大的 `rho`。结果就可能偏得很多。

HLL 的解决方法是分桶。

它不做一次观察，而是做很多次观察。

## 4. 分桶

设参数为 `p`。

寄存器数量为：

```text
m = 2^p
```

本项目默认：

```text
p = 12
m = 4096
```

处理一个元素时：

1. 计算 64 位哈希值。
2. 取前 `p` 位作为桶号。
3. 剩下的位用来计算 `rho`。
4. 当前桶只保存最大的 `rho`。

伪代码如下：

```text
h = hash(value)
index = h 的前 p 位
rank = h 剩余部分的 rho
M[index] = max(M[index], rank)
```

这里 `M` 就是寄存器数组。

每个桶只记录一个很小的整数。

不会保存原始字符串。

## 5. 一个 add 到底做了什么

假设：

```text
p = 4
```

那么有：

```text
m = 16
```

如果某个哈希值开头是：

```text
1010 00101...
```

前 4 位是：

```text
1010
```

所以桶号是 10。

剩下部分是：

```text
00101...
```

第一个 `1` 在第 3 位。

所以：

```text
rho = 3
```

最后做：

```text
M[10] = max(M[10], 3)
```

如果 `M[10]` 原来已经是 5，就不修改。

如果原来是 2，就改成 3。

## 6. 为什么重复元素不会重复计数

同一个输入会得到同一个哈希值。

所以它会：

- 落到同一个桶；
- 得到同一个 `rho`。

第一次加入后，寄存器已经记录了这个值。

再次加入时：

```text
max(old, same_value)
```

结果不会继续变大。

因此 HLL 天然可以处理重复数据。

## 7. 怎样得到最终估计值

设第 `j` 个寄存器为：

```text
M[j]
```

先计算：

```text
sum = Σ 2^(-M[j])
```

然后计算：

```text
E = alpha_m * m * m / sum
```

`alpha_m` 是修正常数。

本项目使用：

```text
m = 16   -> 0.673
m = 32   -> 0.697
m = 64   -> 0.709
m >= 128 -> 0.7213 / (1 + 1.079 / m)
```

本项目限制：

```text
4 <= p <= 14
```

所以最小 `m` 是 16。

这样上面的修正常数范围完整覆盖本项目。

HLL 的典型相对标准误差约为：

```text
1.04 / sqrt(m)
```

当 `p = 12` 时：

```text
m = 4096
误差约为 1.625%
```

这个数是统计意义上的典型误差，不是每次运行都保证小于 1.625%。

## 8. 小数据时为什么要修正

数据较少时，大量寄存器还是 0。

这时直接使用原始估计公式不够好。

设空寄存器数量为：

```text
V
```

如果原始估计比较小，并且 `V > 0`，使用：

```text
E = m * ln(m / V)
```

本项目采用条件：

```text
原始估计 <= 2.5 * m
```

这叫线性计数修正。

直觉很简单：

- 数据少时，空桶多；
- 数据变多时，空桶越来越少。

所以空桶数量也能提供信息。

## 9. merge 为什么很简单

假设有两个 HLL：

```text
A
B
```

它们使用相同的：

- `p`；
- 哈希函数。

对任意一个桶 `i`：

```text
A[i] = A 数据中这个桶见过的最大 rho
B[i] = B 数据中这个桶见过的最大 rho
```

两份数据合起来后，应该是：

```text
max(A[i], B[i])
```

所以 merge 只需要：

```text
for 每个寄存器 i:
    A[i] = max(A[i], B[i])
```

这也是 HLL 很适合分布式系统的原因。

不同机器可以先独立统计。

最后只需要合并 HLL，不需要传输所有原始数据。

## 10. 第一阶段：HLL0

第一阶段只关心算法正确。

寄存器直接使用：

```cpp
std::vector<uint8_t> registers;
```

每个寄存器占 1 字节。

需要完成三个函数：

```cpp
void add(const std::string& value);
double estimate() const;
void merge(const HLL0& other);
```

### add

要做四步：

```text
1. hash64(value)
2. 计算桶号
3. 计算 rho
4. 更新对应寄存器的最大值
```

### estimate

要做四步：

```text
1. 遍历所有寄存器
2. 计算 sum(2^-M[i])
3. 计算原始估计
4. 必要时做小基数修正
```

### merge

要做两步：

```text
1. 检查 p 是否相同
2. 每个寄存器取最大值
```

这一阶段不要考虑压缩、序列化或稀疏表示。

先把 HLL 本身写对。

## 11. 第二阶段：DenseHLL

HLL0 每个寄存器使用 8 位。

但本项目里寄存器值最多只需要 6 位。

所以第二阶段把寄存器连续压成 6 位。

这一步不改变 HLL 数学算法。

只改变数据的存放方式。

还会增加两个工程功能：

- `dump/load`：保存和恢复一个 HLL；
- estimate 缓存：数据没变时，不重复计算。

详细说明见：

`任务1_密集存储.md`

## 12. 第三阶段：SparseHLL

当数据很少时，4096 个寄存器中大部分都是 0。

即使每个寄存器只占 6 位，也有很多空间在保存 0。

第三阶段只保存非零寄存器。

当非零寄存器越来越多时，再转成密集格式。

这一步的核心是：

```text
数据少 -> sparse
数据多 -> dense
```

逻辑上的 HLL 没有变化。

变化的只是内部表示方式。

详细说明见：

`任务2_稀疏表示.md`

## 14. 项目边界

本项目实现经典 HyperLogLog 的核心版本。

为了让重点落在算法和数据表示上，本项目不加入：

- HLL++ 的经验偏差修正表；
- 面向极端超大基数的额外修正；
- 与 Redis 二进制格式完全兼容的编码；
- 并发更新；
- 网络通信或持久化系统。

这些内容可以作为后续扩展，但不属于八周项目的必做部分。
