# 八周进度与检查点

两人一组，共八周。

每两周检查一次。

只检查代码、测试和对实现的理解。

## 第 1~2 周：完成 HLL0

对应任务文档：`任务0_基础HLL.md`

需要完成：

```text
hash 的使用
bucketIndex
rho
HLL0::add
HLL0::estimate
HLL0::merge
```

本阶段先不要做 6 位压缩。

也不要做 sparse。

检查点 1：

1. 空 HLL 的估计结果为 0。
2. 加入重复元素后，结果不会持续增长。
3. 加入 1000、10000 等不同数量的数据后，估计在合理范围内。
4. 两份 HLL merge 后，与直接处理两份数据的结果一致。
5. 不同 `p` 的 HLL 不能 merge。
6. 能说明 `p`、`m`、桶和 `rho` 分别是什么。

建议测试：

```text
0 个不同元素
1 个不同元素
50 个不同元素
1000 个不同元素
10000 个不同元素
大量重复元素
```

## 第 3~4 周：完成 DenseHLL

需要完成：

```text
6 位 get
6 位 set
DenseHLL::add
DenseHLL::estimate
DenseHLL::merge
cache
dump
load
```

检查点 2：

1. 所有寄存器都能正确 `set -> get`。
2. 能正确处理跨字节寄存器。
3. 修改一个寄存器不会影响相邻寄存器。
4. DenseHLL 和 HLL0 处理同一数据时结果一致。
5. `p = 12` 时正文大小为 3072 B。
6. `dump -> load` 后寄存器状态不变。
7. 连续两次 `estimate()` 能复用缓存。
8. 数据发生修改后缓存会失效。

这一阶段结束时，DenseHLL 应该已经可以单独使用。

## 第 5~6 周：完成 SparseHLL 基础部分

需要完成：

```text
SparseEntry
updateEntry
SparseHLL::add
SparseHLL::estimate
sparseBytes
promote
```

先不用急着写全部 merge 和 load。

检查点 3：

1. 非零 entry 始终按 index 递增。
2. 同一个桶只保留最大的值。
3. 小数据时对象保持 sparse。
4. 小数据时占用小于 dense。
5. sparse 状态的 estimate 正确。
6. `promote()` 前后逻辑寄存器不变。
7. `promote()` 前后 estimate 不变。
8. sparse 大到一定程度后会自动转 dense。

## 第 7~8 周：完成整个项目

需要完成：

```text
Sparse dump
Sparse load
Sparse merge
Dense/Sparse 混合 merge
非法输入检查
随机一致性测试
代码整理
```

检查点 4：

1. 参考测试全部通过。
2. HLL0、DenseHLL、SparseHLL 处理同一数据时结果一致。
3. sparse 和 dense 都能 `dump -> load`。
4. sparse+sparse merge 正确。
5. sparse+dense merge 正确。
6. dense+sparse merge 正确。
7. dense+dense merge 正确。
8. `A.merge(A)` 不改变结果。
9. `A merge B` 与 `B merge A` 的逻辑寄存器状态一致。
10. 非法文件头、非法编码和越界 sparse 数据会被拒绝。
11. 能解释三个版本分别解决了什么问题。

## 最终代码要求

优先级：

```text
正确 > 清楚 > 可测试 > 性能 > 代码短
```

建议：

- 一个函数只做一件主要事情。
- 一个变量只表达一个意思。
- 位运算拆开写。
- 不为了少写几行而使用难懂技巧。
- 注释只解释必要的原因。
- 不写装饰性注释。
- 不要求复杂面向对象设计。
- 不要求继承、虚函数或模板框架。
