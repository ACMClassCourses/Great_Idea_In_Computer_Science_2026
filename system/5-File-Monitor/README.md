## A 问题是什么

编辑器和同步工具怎样发现文件已经变化，而不必让用户手动刷新？本项目用 C++ 观察一个测试目录。Basic 周期性扫描文件大小和修改时间，比较前后快照；Advance 在 Linux 上使用 inotify 接收访问、修改和目录条目变化通知，理解轮询与事件驱动的取舍。监控器读取目录信息并打印日志，测试文件的创建和修改由另一个程序或编辑器完成。

| 阶段 | 工作量 | 难度 | 主要成果 |
| --- | --- | --- | --- |
| Basic | 一周约 10–20 小时 | medium | 非递归的目录轮询监控器 |
| Advance | Basic 后追加六周 | medium；可选阅读含 hard | 使用 inotify、过滤及事件聚合的监控器 |

需要 C++17 编译器。Basic 使用标准库，可在支持 `std::filesystem` 的环境运行；Advance 需要 Linux，可使用已有的 Linux 机器或 WSL 环境。easy 为单一概念或规则，medium 需要处理 API、状态与错误，hard 需要理解并发或复杂系统机制。估时包含基础环境检查，但不包含从零安装整套操作系统。

### Basic：比较目录快照

#### 1 需要回答的问题

| 编号 | 问题 | 回答要求 |
| --- | --- | --- |
| Q1 | 监控程序怎样知道目录发生了变化？ | 说明一次快照保存什么、前后两次如何比较 |
| Q2 | 文件大小与最后修改时间分别表示什么？ | 说明为什么它们不是文件内容本身，也不是精确的操作次数 |
| Q3 | 怎样区分新增、删除和修改？ | 用前后快照中的路径是否存在、元数据是否变化来解释 |
| Q4 | 扫描间隔越短一定越好吗？ | 比较检测延迟与扫描开销；说明扫描之间创建又删除的文件可能被漏掉 |
| Q5 | 旧快照为 `a:(10,1), b:(20,1)`，新快照为 `a:(12,2), c:(20,1)`，应输出什么？ | 括号为大小与修改时间；写出 MODIFY、DELETE、CREATE，并说明单凭这些信息不能认定 b 被重命名为 c |

#### 2 代码任务

用 `map<string, FileInfo>` 保存“相对文件名 → 大小、最后修改时间”。实现一个扫描函数和一个比较函数，时间可以保留为 `filesystem::file_time_type`，不要求转换为日历时间。

运行形式可自行设计，例如 `./monitor 测试目录 轮询次数`。启动时先保存基准快照，随后每隔约一秒扫描一次，共执行指定次数后退出。仅处理指定目录下的普通文件，不递归，不跟随符号链接；子目录跳过。

| 比较结果 | 输出 |
| --- | --- |
| 新快照有、旧快照没有 | `CREATE 文件名` |
| 旧快照有、新快照没有 | `DELETE 文件名` |
| 两边都有，大小或修改时间不同 | `MODIFY 文件名` |
| 两边都有且这两项相同 | 不输出 |

每轮日志按文件名字典序输出，便于复现。初始目录内容只作为基线，不记为新增。目录不存在、无法读取或某次扫描失败时显示错误；不能把失败的扫描当作空目录，产生一批虚假的 DELETE。扫描成功后才能更新基线。

这个阶段只能发现采样时看到的元数据差异，**不能监控纯读取，也不能保证发现所有内容修改**。重命名按“旧路径删除＋新路径创建”处理。监控器本身不创建、删除或修改被监控文件，也不要求多线程。

#### 3 OJ 提交：快照比较（在线评测）

快照比较逻辑是本阶段的可自动评测部分，需提交到课程 OJ。代码框架在 `basic/src/monitor.cpp`，评测数据为纯文本快照对，不依赖真实文件系统行为——你的任务是从两份快照中算出变化日志。

**输入格式**（标准输入）：

```text
N0
<name> <size> <mtime> <type>     （共 N0 行，旧快照）
N1
<name> <size> <mtime> <type>     （共 N1 行，新快照）
```

- `name`：文件名，不含空白字符，仅含字母、数字、`.`、`_`、`-`，长度不超过 64；
- `size`：文件大小，0 ≤ size ≤ 10⁹；
- `mtime`：最后修改时间的逻辑时钟读数，0 ≤ mtime ≤ 10¹⁸（**注意需要 64 位整数**）；
- `type`：`F` 表示普通文件，`D` 表示子目录——**子目录条目必须忽略**，不参与比较；
- 0 ≤ N0, N1 ≤ 100000；同一快照中普通文件名不会重复；条目顺序任意（**不保证有序**）。

**输出格式**（标准输出）：对每个发生变化的**普通文件**输出一行：

| 情况 | 输出 |
| --- | --- |
| 新快照有、旧快照没有 | `CREATE <name>` |
| 旧快照有、新快照没有 | `DELETE <name>` |
| 两边都有，但 size 或 mtime 不同 | `MODIFY <name>` |
| 两边都有且两项都相同 | 不输出 |

所有输出行按文件名的**字典序**（按字节比较，即 ASCII 序）排列，每行一个条目，行内只含操作名、一个空格、文件名。**没有任何变化时输出为空**。重命名按“DELETE 旧名 + CREATE 新名”处理。

**样例输入**（即 Q5 的快照）：

```text
2
a 10 1 F
b 20 1 F
2
a 12 2 F
c 20 1 F
```

**样例输出**：

```text
MODIFY a
DELETE b
CREATE c
```

限制：时间 1 秒（大规模数据点 2 秒），内存 256 MiB。数据点覆盖简单、综合、大规模与健壮性（含目录条目、仅 mtime 变化、全删全建、乱序输入等）情形；大规模数据点要求 O((N0+N1) log(N0+N1)) 或更优的实现，逐一在两份快照间做线性查找会超时。

#### 4 演示与验收

在一个专用测试目录中，启动轮询监控后分别创建、追加、删除文件，每步等待至少两个扫描周期，检查相应日志。另测已有文件作为基线、空目录、子目录被忽略、非法路径、内容不变的重复扫描。

| G3 | 识别访问、修改、创建、删除及移动事件，区分文件与目录 | medium |

| G7 | 对比两种监控方式，整理测试、阅读笔记和 presentation | medium |

#### 2 实现要求与范围

直接调用 Linux inotify API，核心接收过程自行编写。建议单线程使用 `inotify_init1(IN_NONBLOCK | IN_CLOEXEC)`，配合带有限超时的 `poll`；不以 `system("inotifywait")` 或监控库替代。程序只接收文件事件，不读取文件内容来推断事件。

- 用 `inotify_add_watch` 监听指定目录；记录 watch descriptor 与目录路径的关系。
- 关注 `IN_ACCESS`、`IN_MODIFY`、`IN_CREATE`、`IN_DELETE`、`IN_MOVED_FROM`、`IN_MOVED_TO`；同时订阅 `IN_DELETE_SELF`、`IN_MOVE_SELF` 以发现监控目录自身失效。用位运算判断事件掩码，并识别 `IN_ISDIR`、`IN_IGNORED`。同一个事件可能带多个标志。
- 一次 `read` 可能包含多条变长记录。每条占 `sizeof(inotify_event) + len` 字节；先检查剩余长度，注意缓冲区对齐、`len == 0` 和文件名终止符。不要按固定步长处理全部事件。
- Basic 的 CREATE/MODIFY/DELETE 文本格式可以保留；读取通知输出 ACCESS。移动事件先分别输出 MOVED_FROM/MOVED_TO 与 cookie，能够说明同一 cookie 用于关联。跨监控边界可能只收到一半，不要求完整还原重命名。
- 过滤只需一种简单规则，例如只显示 `.txt` 文件，或忽略名称以 `.` 开头的条目。规则作用于日志，不影响必要的状态维护。

**聚合约定：** 对通过过滤的同一路径 MODIFY 事件，保存首次、末次接收时刻和收到的事件条数；连续一秒没有新 MODIFY 后输出一条汇总并清除记录。采用单调时钟检查静默时间，退出时输出尚未完成的汇总。这是“按静默间隔聚合”；持续不断修改时可能一直等待到停止或退出。计数只能称为“收到的通知条数”，不能称为文件真实写了多少次。

**退出与错误：** 定期检查退出条件，空闲和高频事件下都应能退出。若使用 SIGINT，处理函数只设置 `volatile std::sig_atomic_t` 标志，资源释放、输出和容器操作在主循环完成；不要在信号处理函数中操作队列。正确区分 `EAGAIN`、`EINTR` 与真正错误，退出时移除 watch 并关闭描述符。

遇到 `IN_Q_OVERFLOW` 要输出“事件可能丢失”，不能继续宣称日志完整；监控目录被删除、移走或 watch 失效时应提示并结束本次监控。可利用 Basic 快照检查最终目录状态，但快照无法补回全部历史操作。inotify 也不提供每次事件对应的进程身份、读写字节数，不能将本项目当作完整文件审计系统。[inotify(7) 的限制说明](https://man7.org/linux/man-pages/man7/inotify.7.html)

#### 3 测试与比较

在同一测试目录对轮询和事件版分别执行创建、读取、追加、删除、移动与连续修改。记录检测到的类型、重复通知和可观察延迟；计时方法与扫描间隔须说明，不设“必定小于某毫秒”的跨机器验收条件。

重点测试：一个缓冲区有多条事件、无事件时退出、高频事件时退出、过滤生效、聚合超时与退出冲刷、监控目录失效。溢出难以稳定触发时，可将解析和状态处理拆成函数，用人工事件验证错误分支。不要要求每次编辑器保存只产生一条 MODIFY。

## C 问题的来龙去脉与发展过程

最直接的监控办法是反复询问文件当前状态。文件增多或扫描间隔缩短后，重复扫描开销随之增加；采样之间发生又消失的变化还可能无法被看见。事件通知把“主动扫描全部状态”转为“状态变化时接收通知”，但需要额外处理队列、错误和失效情况。

Linux 曾使用 dnotify，后来引入 inotify；inotify 自 Linux 2.6.13 起提供文件系统事件通知。它改善了通知接口，却仍有非递归、事件合并、队列溢出等边界。项目的重点是理解为何改用事件驱动，以及这种改进为何仍不能代替完整历史记录。[Linux inotify 手册](https://man7.org/linux/man-pages/man7/inotify.7.html)
