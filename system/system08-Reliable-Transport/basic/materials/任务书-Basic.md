# 可靠传输协议模拟器：在不可靠的网络上正确传递消息

## A 问题是什么

发送一个数据包，并不意味着对方一定收到；没有收到回复，也不一定意味着数据包丢失，因为回复本身可能丢失或迟到。怎样利用序号、确认和超时重传，让接收方按顺序、无重复地获得消息？本项目用 C++ 在一个程序内部模拟发送方、接收方和网络。Basic 实现一次只发送一个包的停止等待协议；Advance 实现 Go-Back-N 滑动窗口协议，观察丢包、重复和乱序下的行为，并了解可靠性、流量控制与拥塞控制各自解决的问题。

| 阶段 | 工作量 | 难度 | 主要成果 |
| --- | --- | --- | --- |
| Basic | 一周约 10–20 小时 | medium | 支持数据包／确认包丢失与超时重传的停止等待模拟器 |
| Advance | Basic 后追加六周 | hard | Go-Back-N 模拟器、可复现的实验与协议思想讲解 |

前置知识：C++ 条件、循环、结构体和 `vector`；不要求学过计算机网络。难度综合考虑理解、实现与调试：easy 为单项基础任务，medium 需要组合几个机制，hard 需要维护相互影响的状态并解释异常情况。Advance 的难点主要是窗口、确认与计时器的配合。

全部代码采用 **C++17、单程序、内存模拟**：用数组或 `vector` 保存消息和事件，用整数表示时间。无需 Socket、多线程、真实网络、图形界面或完整 TCP。流量控制与拥塞控制要求阅读和讲解，不要求实现。

#### 2 代码任务与模拟规则

程序接收一组消息、超时阈值 `RTO`、最大模拟时刻 `max_tick` 和丢包规则，输出事件日志与最终结果。消息用 `vector<string>` 保存，序号为 `0…N-1`，同一消息重传时序号与内容保持不变。输入形式可以自行设计，直接用 C++ 初始化列表保存测试配置也可以，无需编写复杂的配置解析器。

**先统一以下约定：**

| 对象 | 本项目中的含义 |
| --- | --- |
| `DATA(i, content)` | 序号为 `i` 的完整消息；暂不拆分长消息、不模拟内容损坏 |
| `ACK(k)` | 接收方已经交付所有序号小于 `k` 的消息，下一条期待 `k`；因此 `ACK(1)` 确认的是第 0 条消息 |
| `expected` | 接收方下一条期待的序号，初始为 0 |
| 模拟时间 | 从 0 开始的整数；Basic 中数据包和 ACK 的单程延迟均为 1，正常往返需要 2 个时间单位 |
| 超时 | 首次发送或重传后，在 `当前时刻 + RTO` 仍未确认时重传；默认 `RTO = 4` |
| 丢包规则 | 按“包类型、编号、该编号的第几次发送”指定；例如丢弃第一次发送的 `ACK(2)` |

数据包与 ACK 的发送次数分别按各自编号计数，从 1 开始，丢弃的发送也计入次数。规则仅影响命中的那一次发送，其余发送正常到达。`RTO` 必须为正整数，`max_tick` 必须为非负整数；非法配置报错。序号在一次模拟中不循环使用，避免增加序号回绕的实现负担。

**必须实现的行为：**

1. 发送方从 `DATA(0)` 开始，一次只保留一个未确认包；收到当前包的有效确认后，立即发送下一条消息。
2. 接收方仅在 `i == expected` 时把内容追加到交付结果中，并增加 `expected`；重复包或非预期序号不追加。每次收到数据包，都回复当前的 `ACK(expected)`。
3. 发送方收到当前消息 `i` 对应的 `ACK(i+1)` 才前进；旧确认或无效确认不能使状态倒退、跳过消息或重置计时器。
4. 没有收到有效确认且计时器到期时，重传当前包并重新计时。接收方是否已经收到它，由接收方自己的状态判断。
5. 用一个事件表保存尚未到达的包。循环推进整数时间，每个时刻先处理全部到达事件，再判断超时；同一时刻的到达事件按加入事件表的顺序处理。无需真实等待或 `sleep`。

建议将代码拆成发送方、接收方、网络模拟与主循环四个部分，用结构体和普通函数即可。发送方只能通过收到的 ACK 和超时事件更新传输状态，不能直接读取接收方结果或提前查看丢包规则。扫描 `vector` 取出当前时刻的事件即可完成 Basic。

发送方确认全部 `N` 条消息后结束，输出 `SUCCESS`，并检查交付的序号和内容与原始序列完全一致；空消息列表在时刻 0 成功。若处理完 `max_tick` 时刻后仍未全部确认，输出 `INCOMPLETE` 和已交付数量，不能把“接收方已收到”直接当成“发送方已确认”。这表示在给定时间内未完成，不代表协议一定有错误。

#### 3 示例与验收

输入消息 `A、B、C`，序号分别为 `0、1、2`，设置 `RTO = 4`、`max_tick = 100`，只丢弃第一次发送的 `ACK(2)`。关键过程应为：

| 时刻 | 事件 |
| --- | --- |
| 0 | 发送 `DATA(0, A)` |
| 1 | 接收方交付 A，返回 `ACK(1)` |
| 2 | 发送方收到 `ACK(1)`，发送 `DATA(1, B)` |
| 3 | 接收方交付 B，返回的 `ACK(2)` 被丢弃 |
| 6 | 发送方超时，重传 `DATA(1, B)` |
| 7 | 接收方识别重复包，不再交付 B，重新返回 `ACK(2)` |
| 8 | 发送方收到 `ACK(2)`，发送 `DATA(2, C)` |
| 9 | 接收方交付 C，返回 `ACK(3)` |
| 10 | 发送方收到 `ACK(3)`，传输完成 |

预期结果为 `A、B、C`，数据包共发送 4 次，其中重传 1 次；ACK 共发送 4 次，其中 1 次被丢弃；完成时刻为 10。没有丢包时，同一组消息应在时刻 6 完成。

提交 C++17 源码、编译运行说明、Q1–Q5 回答和至少六组测试：正常传输、数据包丢失、ACK 丢失、同一包连续两次丢失、空消息列表、达到时间上限仍未完成。成功案例检查消息内容、顺序与数量，不能只检查“程序运行结束”。Basic 不要求 presentation；基础评测题号为 3283，可用该题 AC 记录替代对应自动测试结果。

#### 5 学习边界

这里的“可靠”指在给定模型中按序、无重复地交付内容。能够最终完成，还需要网络最终允许数据和确认通过，并给予足够的重试时间。程序暂不模拟内容损坏、机器崩溃和重启；它也不提供应用操作在崩溃后仍“恰好执行一次”的保证。
