## A 问题是什么

发送一个数据包，并不意味着对方一定收到；没有收到回复，也不一定意味着数据包丢失，因为回复本身可能丢失或迟到。怎样利用序号、确认和超时重传，让接收方按顺序、无重复地获得消息？本项目用 C++ 在一个程序内部模拟发送方、接收方和网络。Basic 实现一次只发送一个包的停止等待协议；Advance 实现 Go-Back-N 滑动窗口协议，观察丢包、重复和乱序下的行为，并了解可靠性、流量控制与拥塞控制各自解决的问题。

| 阶段 | 工作量 | 难度 | 主要成果 |
| --- | --- | --- | --- |
| Basic | 一周约 10–20 小时 | medium | 支持数据包／确认包丢失与超时重传的停止等待模拟器 |
| Advance | Basic 后追加六周 | hard | Go-Back-N 模拟器、可复现的实验与协议思想讲解 |

前置知识：C++ 条件、循环、结构体和 `vector`；不要求学过计算机网络。难度综合考虑理解、实现与调试：easy 为单项基础任务，medium 需要组合几个机制，hard 需要维护相互影响的状态并解释异常情况。Advance 的难点主要是窗口、确认与计时器的配合。

全部代码采用 **C++17、单程序、内存模拟**：用数组或 `vector` 保存消息和事件，用整数表示时间。无需 Socket、多线程、真实网络、图形界面或完整 TCP。流量控制与拥塞控制要求阅读和讲解，不要求实现。

#### 2 代码任务与模拟规则

程序接收一组消息、超时阈值 `RTO`、最大模拟时刻 `max_tick` 和丢包规则，输出事件日志与最终结果。消息用 `vector<string>` 保存，序号为 `0…N-1`，同一消息重传时序号与内容保持不变。输入形式可以自行设计，直接用 C++ 初始化列表保存测试配置也可以，无需编写复杂的配置解析器。

**先统一以下约定：**

| 对象 | 本项目中的含义 |
| --- | --- |
| `DATA(i, content)` | 序号为 `i` 的完整消息；暂不拆分长消息、不模拟内容损坏 |
| `ACK(k)` | 接收方已经交付所有序号小于 `k` 的消息，下一条期待 `k`；因此 `ACK(1)` 确认的是第 0 条消息 |
| `expected` | 接收方下一条期待的序号，初始为 0 |
| 模拟时间 | 从 0 开始的整数；Basic 中数据包和 ACK 的单程延迟均为 1，正常往返需要 2 个时间单位 |
| 超时 | 首次发送或重传后，在 `当前时刻 + RTO` 仍未确认时重传；默认 `RTO = 4` |
| 丢包规则 | 按“包类型、编号、该编号的第几次发送”指定；例如丢弃第一次发送的 `ACK(2)` |

数据包与 ACK 的发送次数分别按各自编号计数，从 1 开始，丢弃的发送也计入次数。规则仅影响命中的那一次发送，其余发送正常到达。`RTO` 必须为正整数，`max_tick` 必须为非负整数；非法配置报错。序号在一次模拟中不循环使用，避免增加序号回绕的实现负担。

**必须实现的行为：**

1. 发送方从 `DATA(0)` 开始，一次只保留一个未确认包；收到当前包的有效确认后，立即发送下一条消息。
2. 接收方仅在 `i == expected` 时把内容追加到交付结果中，并增加 `expected`；重复包或非预期序号不追加。每次收到数据包，都回复当前的 `ACK(expected)`。
3. 发送方收到当前消息 `i` 对应的 `ACK(i+1)` 才前进；旧确认或无效确认不能使状态倒退、跳过消息或重置计时器。
4. 没有收到有效确认且计时器到期时，重传当前包并重新计时。接收方是否已经收到它，由接收方自己的状态判断。
5. 用一个事件表保存尚未到达的包。循环推进整数时间，每个时刻先处理全部到达事件，再判断超时；同一时刻的到达事件按加入事件表的顺序处理。无需真实等待或 `sleep`。

建议将代码拆成发送方、接收方、网络模拟与主循环四个部分，用结构体和普通函数即可。发送方只能通过收到的 ACK 和超时事件更新传输状态，不能直接读取接收方结果或提前查看丢包规则。扫描 `vector` 取出当前时刻的事件即可完成 Basic。

发送方确认全部 `N` 条消息后结束，输出 `SUCCESS`，并检查交付的序号和内容与原始序列完全一致；空消息列表在时刻 0 成功。若处理完 `max_tick` 时刻后仍未全部确认，输出 `INCOMPLETE` 和已交付数量，不能把“接收方已收到”直接当成“发送方已确认”。这表示在给定时间内未完成，不代表协议一定有错误。

#### 3 示例与验收

输入消息 `A、B、C`，序号分别为 `0、1、2`，设置 `RTO = 4`、`max_tick = 100`，只丢弃第一次发送的 `ACK(2)`。关键过程应为：

| 时刻 | 事件 |
| --- | --- |
| 0 | 发送 `DATA(0, A)` |
| 1 | 接收方交付 A，返回 `ACK(1)` |
| 2 | 发送方收到 `ACK(1)`，发送 `DATA(1, B)` |
| 3 | 接收方交付 B，返回的 `ACK(2)` 被丢弃 |
| 6 | 发送方超时，重传 `DATA(1, B)` |
| 7 | 接收方识别重复包，不再交付 B，重新返回 `ACK(2)` |
| 8 | 发送方收到 `ACK(2)`，发送 `DATA(2, C)` |
| 9 | 接收方交付 C，返回 `ACK(3)` |
| 10 | 发送方收到 `ACK(3)`，传输完成 |

预期结果为 `A、B、C`，数据包共发送 4 次，其中重传 1 次；ACK 共发送 4 次，其中 1 次被丢弃；完成时刻为 10。没有丢包时，同一组消息应在时刻 6 完成。

提交 C++17 源码、编译运行说明、Q1–Q5 回答和至少六组测试：正常传输、数据包丢失、ACK 丢失、同一包连续两次丢失、空消息列表、达到时间上限仍未完成。成功案例检查消息内容、顺序与数量，不能只检查“程序运行结束”。Basic 不要求 presentation；基础评测题号为 3283，可用该题 AC 记录替代对应自动测试结果。

#### 5 学习边界

这里的“可靠”指在给定模型中按序、无重复地交付内容。能够最终完成，还需要网络最终允许数据和确认通过，并给予足够的重试时间。程序暂不模拟内容损坏、机器崩溃和重启；它也不提供应用操作在崩溃后仍“恰好执行一次”的保证。

#### 2 滑动窗口怎样实现

停止等待相当于发送窗口大小为 1。窗口大小为 `W` 时，发送方最多允许 `W` 个不同序号的包处于“已发送、未确认”状态。GBN 接收方只接受当前期待的包；如果前面的包迟到或丢失，后面先到的包会被丢弃，等待发送方重传。

沿用 Basic 的消息、累计 ACK 与事件处理约定，新增三个发送状态：

| 状态 | 含义 |
| --- | --- |
| `base` | 最早尚未确认的消息序号，初始为 0 |
| `next` | 下一条尚未首次发送的消息序号，初始为 0 |
| `W` | 固定的发送窗口大小，要求为正整数 |

实现以下规则，并在日志中显示 `base`、`next` 与 `expected` 的变化：

1. **填满窗口：** 初始化及收到新确认后，只要 `next < N` 且 `next - base < W`，就发送 `DATA(next)` 并增加 `next`。每次填充按序号递增发送。
2. **累计确认：** 收到满足 `base < k <= next` 的 `ACK(k)`，将 `base` 更新为 `k`，随后填充窗口。旧 ACK、重复 ACK 和超过 `next` 的 ACK 均忽略，不重置计时器。
3. **单个计时器：** 窗口从空变为非空时启动计时器，截止时间为 `当前时刻 + RTO`；有效 ACK 推进 `base` 后，若仍有未确认包，重新按此规则计时，否则停表。仅向一个非空窗口补发新包，不改变原计时器。
4. **超时重传：** 超时时，按序重传 `[base, next)` 中的所有包，并重新计时；`next` 不回退。这是 GBN 的关键，本项目不实现快重传。
5. **接收与交付：** 仍然只交付 `i == expected` 的包；其余包直接丢弃且回复当前 `ACK(expected)`，不缓存乱序包。`base == N` 才表示发送方完成。

例如 `W = 3`，发送方发出 `0、1、2`，其中 `1` 丢失。接收方交付 `0` 后期待 `1`，即使 `2` 到达也不交付，并回复 `ACK(1)`。只要没有更大的有效确认，在等待超时后，发送方就从当前 `base` 开始重传所有已发送但未确认的包；若窗口里已有后来补发的包，它们也一起重传。GBN 因而可能重发已经到过接收方、但当时不能按序交付的包。

#### 3 模拟网络与实验

网络仍然用事件表实现，按“包类型、编号、第几次发送”配置以下一种行为；没有匹配规则的发送，单程延迟为 1。每个匹配键最多一条规则。

| 行为 | 配置含义 | 示例 |
| --- | --- | --- |
| 丢失 | 本次发送不产生到达事件 | 第一次发送的 `DATA(1)` 丢失 |
| 延迟 | 指定本次发送到到达的正整数时间差 | 第一次发送的 `DATA(0)` 延迟 5，后发的包可能先到 |
| 重复 | 为本次发送生成两个内容相同的到达事件，分别指定正整数延迟 | `ACK(2)` 的第一次发送分别在 1、3 个时间单位后到达 |

数据与 ACK 两个方向都支持上述行为。复制出的事件不再次应用规则，也不算协议端的新发送；不同到达时间自然产生乱序。同一时刻仍先处理全部到达事件，再检查超时。使用 `vector` 扫描或排序即可，不要求优先队列。确定性规则是必做；随机丢包是可选实现，若使用须保存随机种子。

实验至少覆盖下列四组，每组保留配置和统计表，并选一段日志解释原因：

| 实验 | 配置与需要观察的内容 |
| --- | --- |
| 正常传输 | 12 条消息、`RTO = 4`、无异常，比较 `W = 1、2、4`；应分别在时刻 24、12、6 完成 |
| 丢失与重复 | 分别丢弃一个窗口前部的数据包、一个 ACK；再复制一个数据包和一个 ACK，验证恢复和不重复交付 |
| 乱序与迟到 | 让某个包的首次发送延迟 5，其余延迟 1；解释接收方为何丢弃后到序号，以及迟到原包与重传包怎样处理 |
| 超时阈值 | 同一组延迟配置下比较 `RTO = 1、4、8`；观察过早重传、等待与完成时间，不能只比较发送包数 |

统计总数据发送次数、其中的重传次数、ACK 发送次数、交付数量和完成时刻；数据包第一次发送后的每次发送都算重传。成功案例还可报告“消息数／完成时间”，空输入记为不适用。另验收 `W = 1` 与 Basic 行为一致、`W > N`、全部确认后迟到的旧包不改变结果、持续丢包到达时间上限仍正常退出。成功时允许丢弃事件表中剩余的迟到副本。

**实验模型边界：** 本项目允许同一时刻发出多个包，不建模链路带宽、路由器队列和真实发送耗时；统计体现该模型下的等待与重传代价，不能直接当作真实网络带宽。比较方案时固定消息、延迟和异常规则，并说明规则触发情况；随机实验不能仅凭相同种子就认定经历了相同丢包过程。

## C 问题的来龙去脉与发展过程

可靠传输的出发点是：底层网络可能丢失、延迟或重复数据，上层应用却需要完整、有序的结果。自动重传请求（ARQ）把接收方反馈与发送方重试结合起来；停止等待最容易理解，而滑动窗口允许多个包同时在途中，用流水线减少等待造成的空闲。GBN 与 SR 则在重传成本、接收缓存和状态复杂度之间作出不同取舍。这是本项目从 Basic 到 Advance 的学习主线。[《计算机网络技术基础》配套课件](https://www.stpt.edu.cn/_upload/article/files/7f/e8/3c4405d3418aae49fd8eb73f250d/c608d9cb-86c6-4e8f-bb8b-dc35406a8dbf.pdf)、[Kurose 与 Ross 课件](https://gaia.cs.umass.edu/kurose_ross/ppt.php)

TCP 将可靠传输机制用于端到端的字节流服务。1981 年的 RFC 793 是其重要规范，其中已经包含序号、确认、重传和基于接收窗口的流量控制。随着网络规模增长，拥塞控制进一步关注网络整体的承载能力；仅让接收方来得及处理，并不足以避免中间网络拥堵。GBN 是学习滑动窗口的一种简化模型，不能直接等同于完整 TCP。[RFC 793](https://www.rfc-editor.org/rfc/rfc793.html)、[RFC 5681](https://www.rfc-editor.org/rfc/rfc5681.html)

后续规范不断细化具体机制，例如 2009 年 RFC 5681 整理经典 TCP 拥塞控制算法，2011 年 RFC 6298 规定重传计时器的计算；2022 年 RFC 9293 汇总 TCP 核心规范并取代 RFC 793。presentation 可围绕“丢了怎么办 → 等待太多怎么办 → 接收方太慢怎么办 → 网络太堵怎么办”组织发展脉络，并将问题演进与这些规范节点对应起来。[RFC 6298](https://www.rfc-editor.org/rfc/rfc6298.html)、[RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html)
