## A 问题是什么

文件修改后，怎样保留旧版本、查看历史，并让两条开发路线分别继续演进？本项目用 C++ 在内存中模拟版本管理。Basic 用完整快照实现暂存、提交和历史查看；Advance 用 Blob、Tree、Commit 组织对象，增加分支与版本恢复，理解内容寻址、不可变对象和分支引用。代码不调用真实 Git，也不修改电脑上的文件或仓库。

| 阶段 | 工作量 | 难度 | 主要成果 |
| --- | --- | --- | --- |
| Basic | 一周约 10–20 小时 | easy | 单条历史上的内存快照管理器 |
| Advance | Basic 后追加六周 | hard | 使用对象存储、支持分支与切换的 Mini Git |

前置知识为 C++ 字符串、映射和结构体。easy 表示按明确规则处理单项状态，medium 表示组合数据结构或解释实验，hard 表示需要协调对象图、引用与状态恢复。Advance 的难点是对象间关系，不要求实现网络协议或真实 Git 文件格式。

### Basic：线性版本快照

#### 1 需要回答的问题

| 编号 | 问题 | 回答要求 |
| --- | --- | --- |
| Q1 | 版本控制解决什么问题？为什么仅保存最新文件不够？ | 举出查看旧内容或追溯修改的例子 |
| Q2 | 真实 Git 中工作区、暂存区和提交分别是什么？ | 说明 `add` 与 `commit` 的区别；指出本项目将编辑与暂存合成了一条教学命令 |
| Q3 | 快照与“只记录变化”有什么区别？ | 用两个文件、两次提交解释完整版本包含哪些内容 |
| Q4 | 后续修改为什么不能改变已经生成的提交？ | 解释复制快照与共享可变对象的区别 |
| Q5 | 首次提交含 `a=one,b=two`，下一次只暂存 `a=three` 后提交，各版本分别含什么？ | 写出两份完整快照，说明未修改的 b 是否保留 |

#### 2 代码任务

Basic 编程任务对应 [ACM Class OnlineJudge 3257. MiniGit](https://acm.sjtu.edu.cn/OnlineJudge/problem/3257)。**具体输入输出格式、命令参数、输入保证、错误处理和样例均以 OJ 题面为准。**

使用 `map<string,string>` 表示暂存区，使用 `vector<Commit>` 保存提交；每个 Commit 记录编号、父提交编号、说明和完整文件映射。编号从 1 递增，第一条提交没有父提交。Basic 只有一条提交历史。

所有文件均通过单个文件名标识。文件内容由 `add` 后的输入行提供，全部保存在内存中，不读取真实文件系统；多级路径留到 Advance 实现。

| 教学命令 | 实现目标 |
| --- | --- |
| `add` | 读取输入内容，更新暂存区中的指定文件 |
| `commit` | 将整个暂存区复制成不可变快照，记录父提交和提交说明 |
| `log` | 从最新提交到最早提交查看历史 |
| `show` | 查看指定快照中的文件，核对旧版本 |
| `exit` | 结束程序 |

这里的教学 `add` 把“输入文件内容＋暂存”合成一步，**真实 Git 的 `git add` 是从工作区读取文件**。提交后暂存区保留整份文件映射，下一次只更新有变化的文件；不要在提交后清空它。

### Advance：对象存储与分支

#### 1 Goals 与难度

G1–G7 均需完成，G6 选择一个阅读方向。

| Goal | 完成要求 | 难度 |
| --- | --- | --- |
| G1 | 理解 Blob、Tree、Commit、Index、Branch 和 HEAD，画出一次提交的对象关系 | medium |
| G2 | 实现对象序列化与去重存储，相同对象复用同一 ID | medium |
| G3 | 支持多级路径，将暂存映射构造成 Tree，再由 Commit 恢复完整映射 | hard |
| G4 | 实现 `branch`、`checkout` 及沿当前分支查看历史，保护未提交修改 | hard |
| G5 | 比较完整快照复制与对象复用，验证分支独立演进与旧版本恢复 | medium |
| G6 | 选择一个方向阅读并解释其设计取舍 | 见方向表 |
| G7 | 整理源码、测试、阅读笔记及 presentation，讲清发展背景和演示中的对象变化 | medium |

#### 2 代码实现要求

复用 Basic 的教学 `add` 命令，现在文件名可以是 `src/main.cpp` 等相对路径。路径每段非空，不含 `.`、`..`，不以 `/` 开头；不需要实现独立目录创建。拒绝同一路径既当文件又当目录，例如同时存在 `a` 与 `a/b`。

| 数据 | 保存什么 |
| --- | --- |
| Blob | 一个文件的完整内容 |
| Tree | 子条目的名称、类型及对象 ID；子条目按名称排序 |
| Commit | 根 Tree ID、父 Commit ID、提交说明 |
| Object Store | 对象 ID → 不可变对象 |
| Branch | 分支名 → 当前 Commit ID |
| HEAD | 当前分支名；本项目只支持附着在分支上的 HEAD |

可以先把“对象类型＋字段长度＋字段内容”序列化为字符串，用 `map<string, int>` 对序列化结果分配稳定的内部编号。相同序列化内容必须复用 ID，不同内容不能被误认为同一对象。这是内容去重的教学实现；无需自己写 SHA。若使用哈希作查找键，必须比较原序列化内容以处理碰撞，不能认为一个短哈希绝不冲突。

- `commit` 从暂存区构建 Blob 和递归 Tree，保存 Commit，并只移动当前分支引用；不修改旧对象。程序默认分支为 `main`。
- `branch 名称` 在当前提交处创建分支，不自动切换。无提交时不能创建分支，重名须报错。
- `checkout 名称` 将 HEAD 指向目标分支，并从其 Commit 恢复暂存区中的**完整**文件映射；目标版本没有的文件也须移除。若暂存区内容不同于当前提交，拒绝切换并提示先提交。
- `log` 从当前分支的提交沿 parent 追溯，不能把另一条分支上不可达的提交混入历史。
- 保留 `show` 作验证接口；不要求 `merge`、`rebase`、删除文件、持久化或兼容 `.git` 格式。

验证一次分叉：在 C1 创建 `dev`，切到 dev 修改并提交 C2，再切回 main 修改另一文件并提交 C3。应有 C2、C3 的父提交均为 C1；两条分支各自恢复正确内容，`log` 分别沿自己的祖先输出。

G5 比较至少三次提交，其中包含相同内容和局部修改。统计“整份快照保存的内容字节数”与“唯一 Blob 内容字节数”，并另外统计对象数量。后者不包含 Tree、Commit、映射与字符串容器开销，不能直接称为程序实际内存。

## C 问题的来龙去脉与发展过程

版本管理从为单个文件保存历史，发展到集中管理团队仓库，再发展出每个参与者都能在本地保存历史与提交的分布式方式。2005 年，Linux 内核开发社区对速度、分支和分布式协作的需求促成了 Git 的诞生。[Pro Git：Git 简史](https://git-scm.com/book/zh/v2/起步-Git-简史)

Git 用对象和引用描述版本关系，使“保存内容”与“分支指向哪个版本”分开。逻辑上是快照，存储时又可共享相同对象；后续包文件机制还能采用差分表示进一步节省空间。本项目先复制完整快照，再实现对象复用，借此观察两种层次的设计。[Pro Git：Git 对象](https://git-scm.com/book/zh/v2/Git-内部原理-Git-对象)、[Pro Git 第 10 章](https://git-scm.com/book/zh/v2)
