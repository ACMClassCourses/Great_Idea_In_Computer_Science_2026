# LZW 压缩：Advance（进阶阶段）— 从编号到无损还原

## 项目介绍

Basic 把大写字母串变成了字典编号。现在的问题是：解码程序没有见过原文，也不能读取编码程序建立的字典，它能否按照双方约定的规则，仅凭编号还原数据？你将把 LZW 扩展到任意字节，实现独立解码，并让每个编号占用相同的存储空间，再比较不同数据的实际压缩效果。

先修要求：完成 [Basic](../basic/README.md)，能解释字典更新与末尾输出；熟悉数组、字符串，以及按字符串查找编号的容器（如 `std::map`）。建议在 Basic 后追加 **6 周**，与 Basic 合计 7 周。可继续使用 C++17，用字符串保存片段、用数组保存字节；字节数组就是按顺序保存一组字节的容器。字节的含义见下文，真实文件读写为选做。

## 简要算法介绍

编码过程仍然是：尽量延长当前片段，直到再接一个字节就不在字典中，然后输出当前片段的编号、添加新词条。现在不只处理 A–Z：一个二进制位只能是 0 或 1，8 位组成 1 字节，可以表示 `0–255` 共 256 种值。初始字典中，值为 0 的单字节对应编号 0，值为 1 的单字节对应编号 1，依此类推，新词条从 `256` 开始。例如在 UTF-8 这种把文字转换为字节的编码方式中，一个常见汉字占 3 字节；本项目逐个处理这些字节，不把整个汉字当成一个初始词条。

解码前，先按下文的存储规则把每两个字节还原为一个编号；空输入直接返回空输出。对非空输入，解码程序先检查第一个编号在 `0–255` 内，输出它代表的单字节，并把这段内容记为 `prev`（上一段）。之后每读到编号 `k`，就恢复下一段内容 `entry`（当前段）。下面的 `+` 表示拼接，`prev[0]` 表示 `prev` 的第一个字节：

1. 若 `k` 已在字典中，取出对应字符串 `entry`。
2. 若 `k` 恰好等于下一个可分配编号、字典未满且已有 `prev`，则 `entry = prev + prev[0]`。
3. 其他未定义编号报错。
4. 输出 `entry`；字典未满时加入 `prev + entry[0]`，最后令 `prev = entry`。

编码程序遇到新片段时，添加的词条是“刚输出的片段 + 下一段的第一个字节”。解码程序虽然晚一步读到下一段，也能按同样的规则添加词条，因此不需要传输完整字典。

例如 `ABABABA` 编码为 `65 66 256 258`。这里 A、B 的字节值分别为 65、66，因此初始编号也为 65、66，与 Basic 中从 A=0 开始的约定不同。读到最后的 `258` 时，解码字典尚未保存它，但上一段为 `AB`，故可推出 `ABA`。请用逐步字典表解释这一特殊情况，不能把所有未知编号都按此处理。

## 必做任务与格式约定

| 编号 | 任务 | 完成证据 |
| --- | --- | --- |
| G1 | 任意字节编码 | 能处理值为 0、255 的字节及文本转换成的字节；字节值 0 与文字字符 `0` 不同 |
| G2 | 独立解码 | 解码器只接收编码结果，普通和特殊编号均正确 |
| G3 | 固定 16 位存储、字典容量与错误处理 | 编码和解码遵守相同规则，符合格式的数据可还原，不符合格式的数据会报错 |
| G4 | 先编码、再解码的往返验证与大小分析 | 测试记录与实际字节数对比表 |
| G5 | 了解 Huffman 和 LZ77 | 用小例子比较它们与 LZW 如何利用数据中的重复或频率差异 |
| G6 | DEFLATE 或 LZMA 二选一阅读 | 解释组成与解码流程，不要求实现 |
| G7 | 报告与课堂展示 | 展示正确性、实验结论及发展脉络 |

G1–G7 都需完成；G6 只选一条路线。核心 LZW 过程自行实现，不用现成压缩库代替。

编码和解码程序须共同遵守以下教学格式：

- 每个编号固定占 **16 位，也就是 2 字节**，先保存表示较大数值部分的高字节，再保存低字节。例如编号 `258 = 1×256+2`，依次保存值为 `1` 和 `2` 的两个字节；解码时按同一顺序组合。
- 字典最多 **65536** 项，合法编号为 `0–65535`。满后停止添加，继续使用已有字典，不清空。
- “下一个编号”需用能表示 `65536` 的整数类型；到达这个值表示字典已满，不能输出它。不要用最大值只有 `65535` 的整数类型保存这个计数。
- 每次处理一份新输入都将字典恢复为最初的 256 项，不沿用上一次的词条。不额外保存表示“结束”的编号，以整个字节序列的末尾作为结束；空输入对应空输出。
- 非空输入的第一个编号必须在 `0–255`。若编码结果有奇数个字节（最后一个编号不完整），或首编号超出范围，或后续编号大于下一个可分配编号，都应报告错误。

可用内存字节数组完成编解码和全部测试，不必先实现文件读写。本格式不要求兼容 GIF、ZIP 等文件格式。C/C++ 中普通 `char` 可能把大于 127 的字节解释成负数，处理字节值时可使用 `unsigned char` 或 `uint8_t`。

## 实验要求

至少覆盖空输入、单字节、长重复串、普通文本、随机字节、含 `0` 和 `255` 的数据。生成随机数据时固定随机种子，即给随机数生成器指定同一个起始设置，以便再次生成同一组数据。每组验证：

```text
decode(encode(data)) == data
压缩后大小占比 = 编码字节数 / 原始字节数 × 100%
```

这里 `encode` 表示编码函数，`decode` 表示解码函数，`==` 表示逐字节比较两份数据是否完全相同。空输入的占比记为“不适用”；低于 100% 才表示节省空间。`ABABABA` 是 7 字节，4 个 16 位编号占 8 字节，实际变大。统计时应数编码结果实际包含多少字节，而不是屏幕上打印了多少位数字，也不是字典在程序运行时占用了多少内存。

另构造能填满字典的数据，记录词条数确实达到 65536，检查停止添加后仍能正确还原；仅有“很长的输入”不能证明程序处理过字典已满的情况。可以从较长的随机字节开始，并记录新增词条数。还需为上述三类格式错误各设计至少一例：奇数个字节、首编号超出 `0–255`、后续编号跳过下一个可分配编号。本格式没有额外保存用于检查内容是否被改动的信息，因此有些字节即使被改动，也可能仍符合格式，不能保证检测所有损坏。

建议实验表包含：数据类型、生成方式/种子、原始字节数、编码字节数、大小占比、还原是否一致。解释为何重复数据和随机数据的结果不同。

## 算法发展历程

| 时间 | 思想或算法 | 它增加了什么 |
| --- | --- | --- |
| 1952 年 | Huffman 编码 | 常见符号用较短的二进制表示，较少出现的符号用较长的表示 |
| 1977 年 | LZ77 | 用距离与长度引用此前出现的片段 |
| 1978 年 | LZ78 | 建立逐步增长的字符串字典 |
| 1984 年 | LZW | 预置单字符字典，使解码器能同步重建词条 |
| 1990 年代 | DEFLATE | 组合 LZ77 和 Huffman，RFC 1951 在 1996 年明确其格式 |
| 后续 | LZMA 等 | 在字典匹配之外，根据已读内容估计后续数据的概率，再把这种估计用于编码 |

Huffman 利用符号出现次数的差异，字典方法利用重复片段，所以两者可以组合。阅读时分别关注：怎样减少数据量、编号怎样存成字节、需要多少时间和内存。

G5 请用小例子比较“给常见符号分配较短表示”“记录往前找多远、复制多长”“输出边读边建立的字典编号”。G6 可选：

- **DEFLATE**：LZ77 与 Huffman 分别负责什么？解压时如何先还原符号，再复制片段？
- **LZMA**：先把三个名称与作用对应起来：字典匹配找重复片段；上下文概率模型根据已读内容估计接下来出现什么；范围编码把这些概率转换为紧凑的二进制表示。说明它们如何配合，以及节省空间是否需要更多时间或内存。不要求推导概率公式或范围编码细节。
