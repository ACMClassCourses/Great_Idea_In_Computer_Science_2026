# 小模型 Agent 的选择性工具调用

这是一个为期 **8 周** 的低算力 Agent 评测项目。最终不追求做一个复杂的多 Agent 系统，而是研究一个更具体、也更容易验证的问题：

> **小模型能不能在回答前判断“这道题是否值得调用工具”，在减少调用成本的同时保持准确率？**

项目把工具调用看成一个路由决策。模型可以直接回答，也可以调用一个受控工具；路由器需要在准确率、调用次数、延迟和 token 成本之间做出选择。

## 最终要完成什么

### 两种动作

第一版只保留两个动作，避免项目失控：

```text
direct answer       直接回答
tool-assisted answer 调用计算器或固定检索器后回答
```

工具必须是确定、只读、可复现的，例如：

- 四则运算或单位换算器；
- 本地冻结文档库的检索器；
- 预先缓存的结构化查询结果。

不得连接真实邮箱、支付、账号、文件删除或其他有副作用的外部系统。

### 三条系统路径

最终至少实现以下三种基线，并使用同一个模型、同一个 prompt 和同一个工具：

1. **Never tool**：所有问题都直接回答；
2. **Always tool**：所有问题都调用工具；
3. **Selective router**：根据低成本特征决定是否调用工具。

建议额外加入预算相同的随机调用作为对照。路由器可以从问题和 direct 输出中使用以下特征：

- direct 输出的置信度或 log-prob（如果模型提供）；
- 问题长度、数字和运算符；
- 是否包含实体、日期、多跳关系；
- direct 输出长度和格式；
- 检索器 top-1 相似度；
- 工具预计成本。

路由器不能读取测试答案，也不能使用“工具调用后是否正确”作为线上特征。

## 研究假设

主假设：

> 在固定工具调用预算下，使用廉价特征训练的路由器，能够比 Never tool、Always tool 和随机调用取得更好的 accuracy—cost trade-off；收益主要来自 direct 容易失败、tool 确实有帮助的样本。

这个假设可以失败。比如置信度不校准、工具返回质量不稳定，或者路由器的收益只在数学题上存在，都应作为结果报告。

## 数据集与论文

### 课程主数据

建议使用两个小规模轨道，任选一个作为主实验，另一个作为扩展：

**数学轨：GSM8K 小子集**

- 问题有标准答案，适合计算器工具；
- 可以抽取 300–1000 条，按题型分层抽样；
- 工具返回完全确定，容易比较 direct/tool 的真实收益。

**事实/多跳轨：HotpotQA 或 StrategyQA 小子集**

- 适合固定本地文档检索器；
- 可以观察“直接回答错、检索后答对”和“检索增加噪声”的情况；
- 必须预先冻结文档、检索结果和版本，不能运行时访问网页。

如果希望专门练习函数调用格式，可使用 **BFCL（Berkeley Function Calling Leaderboard）** 的小子集；如果希望研究真实 API 轨迹，可阅读 **API-Bank** 或 **ToolBench**，但不建议把完整 ToolBench 作为第一次课程实验。

### 推荐论文

- Schick et al., *Toolformer: Language Models Can Teach Themselves to Use Tools*：理解模型何时、如何调用工具。
- Yao et al., *ReAct: Synergizing Reasoning and Acting in Language Models*：理解推理与行动交替的基本范式。
- Li et al., *API-Bank: A Comprehensive Benchmark for Tool-Augmented LLMs*：了解工具调用数据和 API 轨迹评测。
- Qin et al., *ToolLLM: Facilitating Large Language Models to Master 16000+ Real-world APIs*：了解大规模 API 工具学习，但只作选读。
- Yao et al., *τ-bench: A Benchmark for Tool-Agent-User Interaction in Real-World Domains*：了解多轮工具交互和状态一致性。
- Guo et al., *Language Models are Few-Shot Learners* 中的校准相关实验，或选择一篇 selective prediction / learning-to-defer 入门材料，理解置信度不能直接当作正确率。

论文阅读重点不是复现大模型训练，而是回答：工具动作空间是什么、工具带来什么成本、系统如何判断何时调用、作者如何定义成功。

## 数据格式

`data/questions.jsonl` 每行一个样本：

```json
{"id":"math-001","domain":"math","question":"17 * 6 = ?","answer":"102","tool_expected":true}
```

固定工具输出单独保存，避免因工具版本变化导致实验不可复现：

```json
{"id":"math-001","tool":"calculator","input":"17 * 6","output":"102","cost":1}
```

最终预测记录至少包含：问题 id、路由动作、direct 输出、工具输入和返回、最终答案、是否正确、调用次数、耗时和 token 成本。

## 必须完成的实验

### 实验一：工具是否真的有帮助

对每道题分别运行 direct 和 tool 两条路径，建立四类分桶：

| direct | tool | 含义 |
| --- | --- | --- |
| 对 | 对 | 工具可能没有必要 |
| 对 | 错 | 工具引入噪声或解析错误 |
| 错 | 对 | 工具最有价值的样本 |
| 错 | 错 | 工具无法解决或题目超出范围 |

先做这个实验，再训练路由器。否则无法知道路由器究竟在选择什么。

### 实验二：固定预算下的路由

在开发集上选择阈值或轻量分类器，在测试集上冻结后比较：

- 0% 工具预算：Never tool；
- 25%、50%、75% 工具预算的随机调用；
- Always tool；
- Selective router。

绘制 `accuracy—tool call rate` 和 `accuracy—estimated cost` 曲线，而不是只报一个最优点。

### 实验三：校准与迁移

至少选择一个扩展：

- 检查 direct 置信度与真实正确率是否匹配；
- 在数学开发集学到的阈值迁移到事实问题；
- 加入拒答/升级动作，绘制 coverage—risk 曲线；
- 加入第三个动作：检索或计算，但保持预算约束。

## 测试内容与通过标准

### 工具安全测试

- 计算器只允许白名单运算符和数值；
- 不执行任意 Python、Shell 或网络请求；
- 非法表达式、除零、空输入都返回结构化错误；
- 工具输入和返回都被记录；
- 同一输入重复运行得到同一输出。

### 路由器单元测试

至少覆盖：

- 纯知识题不调用计算器；
- 数值运算题可以调用计算器；
- 工具预算为 0 和 1 时行为正确；
- 预算不能因为四舍五入超过上限；
- direct/tool 结果都正确时不夸大工具收益；
- 工具返回错误时不会把错误结果当成正确答案。

### 评测协议测试

- train/dev/test 按题目 id 或数据来源隔离；
- 阈值和路由器只在 dev 上选择；
- 测试集不参与 prompt、特征选择和预算选择；
- 所有系统使用相同的题目、模型、prompt 和工具返回；
- 至少重复不同随机种子 3 次，报告均值和波动。

### 最终验收

最终测试集至少 200 条，包含 direct 有优势、tool 有优势和两者都失败的题目。项目必须能够：

- 一条命令运行三种基线和路由器；
- 导出逐题路由日志；
- 输出 accuracy、tool-call rate、平均成本和 P95 延迟；
- 绘制 accuracy—cost frontier；
- 分析至少 10 个“工具越用越错”或“工具确实挽救回答”的案例。

不预设路由器一定优于 Always tool。若工具收益只存在于特定题型，或者调用成本抵消了准确率提升，也应如实报告。

## OJ 提交（Basic 核心逻辑的在线评测）

Basic 阶段的两个确定性核心——**安全计算器**与**预算路由**——在课程 OJ（ACMOJ）上有对应题目，代码验收以 OJ 数据点为准。请从 OJ 题目页面（或本仓库 `include/src/`）下载单文件框架 `tool_router.py`，补全 `calc(expr)` 与 `route(items, budget_percent)` 两个 `TODO` 函数后提交。

**输入格式**：第一行为计算查询数 C，随后 C 行每行一个表达式（整行剩余内容，可能含空格）；然后一行为路由批次数 R，每个批次为 `N b` 一行加 N 行 `id d t s`（direct 是否正确、tool 是否正确、工具需求分数）。

**输出格式**：每个计算查询输出一行——整数值或结构化错误码（`ERR_EMPTY` / `ERR_TOO_LONG` / `ERR_SYNTAX` / `ERR_NESTING` / `ERR_OVERFLOW` / `ERR_DIV_ZERO`）；每个路由批次输出两行——`CALL <选中 id 列表>`（按输入顺序，无选中输出 `CALL -`）与 `RESULT <c>/<N> <acc>% <k>/<N> <rate>%`（百分比保留两位小数）。

**关键规则**（完整题面见 `include/README.md`）：

- 除法 `/` 为**向零取整**（C 语义），`-7/2 = -3`；Python 的 `//` 是向下取整，不要直接用于负操作数；
- 没有一元加号（`1++2` 是语法错误）；一元负号可连用；空白字符无语义；
- 预算是 `floor(N × b / 100)`，用整数运算实现，四舍五入会超预算；
- 同分按输入顺序选择；路由决策不得使用 `d`/`t` 正误标签（它们只用于对账）。

评测为全文精确比较，所有测试点时限 2000 ms、内存 256 MiB。数据点分 simple / complex / large / robust 四组（20/30/30/20 分）。

## 项目边界

这是一个可控的工具选择实验，不是生产级 Agent。工具只读、沙盒运行、结果可缓存；不接触真实账号、邮件、支付、文件删除或其他外部副作用。模型“自称不确定”不是事实，必须用真实正确率检查其校准性。
